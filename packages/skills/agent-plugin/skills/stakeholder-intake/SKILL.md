# Stakeholder Intake — small, traceable, source-preserving

Turn mixed stakeholder input into two stable files:

```text
stakeholder-input/<feature>/
├── intake.md       # normalized summary for Analyst
├── manifest.yaml   # source and status inventory
└── sources/        # optional original files; never rewrite
```

`intake.md` is the hand-off. `manifest.yaml` is the audit index. Do not create one file per topic unless the source itself is a separate document.

## When to use

- New feature request arrives as brief, Excel, meeting notes, SOP, chat export, or links.
- Analyst needs a consistent input package before P0/P1.
- Existing intake must be updated with a new source or conflict.

Not this skill:

- Do not make `intent.md`.
- Do not decide unresolved business rules.
- Do not invent acceptance criteria, owners, dates, systems, or policy values.
- Do not edit original source files.

## Inputs

Accept any combination:

- stakeholder words or chat transcript;
- DOCX, PDF, XLSX, CSV, Markdown, images, or links;
- meeting notes, SOP, PRD, process map, or existing Figma URL.

If no file is supplied, capture the stakeholder's words in `intake.md` and mark `Source: conversation` in `manifest.yaml`.

## Output contract

### `intake.md`

Use [assets/intake-template.md](assets/intake-template.md). Keep four states visible:

- `confirmed`: explicitly agreed or written as an existing policy;
- `proposed`: requested or recommended, not approved;
- `needs-clarification`: ambiguous, conflicting, or missing owner;
- `out-of-scope`: explicitly excluded.

Every normalized claim cites a source ID such as `SRC-01` or `SRC-02`.

### `manifest.yaml`

Use [assets/manifest-template.yaml](assets/manifest-template.yaml). One row per source. Record:

- source ID and filename/link;
- type and owner;
- received date when known;
- status (`raw`, `reviewed`, `superseded`);
- topics covered;
- conflicts or handling note.

Do not put sensitive content in the manifest. Keep it an index only.

### `sources/`

Optional. Copy original files unchanged. Safe names only. If a source cannot be copied, keep its link and note why. Never claim a file was archived when it was not.

## Procedure

1. Create `stakeholder-input/<feature>/`.
2. Copy [assets/intake-template.md](assets/intake-template.md) to `intake.md`.
3. Copy [assets/manifest-template.yaml](assets/manifest-template.yaml) to `manifest.yaml`.
4. Inventory every input. Assign stable `SRC-xx` IDs; never reuse an ID for a different source.
5. Copy originals to `sources/` when available. Preserve filename, type, and content.
6. Normalize only what the source says into Request, Users, Scope, Process, Roles, Rules, Data/Integration, and Open Questions.
7. Mark each item `confirmed`, `proposed`, `needs-clarification`, or `out-of-scope`.
8. Add source IDs to claims and open questions. Record conflicts; do not resolve them silently.
9. Run the gate below. Hand off `intake.md` to `blueprint-ftsd` P0/P1.

## Gate

Run from `stakeholder-input/<feature>/`:

```bash
# required files and top-level fields
 test -s intake.md
 test -s manifest.yaml
 grep -q '^Status: \(raw\|reviewed\|ready-for-brainstorm\)$' intake.md
 grep -q '^feature:' manifest.yaml
 grep -q '^sources:' manifest.yaml

# required intake sections
for h in Request Users Scope "Open questions" Sources; do
  grep -q "^## $h$" intake.md || echo "missing section: $h"
done
```

Model check before hand-off:

- Every source used by `intake.md` exists in `manifest.yaml`.
- Every `needs-clarification` item appears in `## Open questions`.
- Every conflict has both source IDs recorded.
- No source file was modified.
- No `intent.md`, Blueprint, design, API, or implementation was generated by this skill.

## Handoff

```text
Input:  stakeholder files / conversation
Output: stakeholder-input/<feature>/intake.md + manifest.yaml + optional sources/
Owner:  Stakeholder / PM / Analyst
Next:   blueprint-ftsd P0 Discover or P1 Brainstorm
Gate:   intake sections, source IDs, statuses, conflicts, and open questions valid
```

Analyst may work from `intake.md` without opening every source. Open `sources/` when verifying a disputed claim.
